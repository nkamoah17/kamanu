# KAM013: a reset read from the request: a refused revoke revokes

A latch whose reset is read from the request (`!Revoke::request since ...`) is cleared by a
request of Revoke, and on an engine that keeps the requests it refuses, a Revoke that was
asked and refused clears it too: a refused revoke revokes, and the guarded action is refused
while the grant stands. Read the completed call: `::request` becomes `::response`.

Level: **error** (`kamanu lint` exits 1). It needs lint's ledger machine (kamanu.fast.ledger), so it is reported for a policy inside step 4's machine that is a ledger policy.

## Example

On an engine whose refusals leave a request in the history:

```dogwood
@id("access_while_granted")
permit (principal, action == Drupe::Action::"Access", resource)
when temporal {
    !Drupe::Action::"Revoke"::request{ input.user: context.input.user, input.resource: context.input.resource }
    since within 24h
    Drupe::Action::"Grant"::response{ input.user: context.input.user, input.resource: context.input.resource }
};
```

lint's finding (line 4, column 29): KAM013 a reset read from the request: the latch is cleared by Revoke::request, and on an engine whose refusals leave a request in the history a refused request stays in the history, so a Revoke that was asked and refused revokes; read Revoke::response (the revoking call completed) instead.

The trace:

1. Grant response (the call completed)
2. Revoke asked: refused
3. Access asked: refused

## The edit

Line 4, column 29: `::request` becomes `::response`.

Note: without the refused Revoke request, Access is permitted.

## Suppressing it

`// kamanu-ignore KAM013: <reason>` at the end of the pattern's line or alone on the line above it;
the reason is required, and the finding stays in the output and the SARIF.
