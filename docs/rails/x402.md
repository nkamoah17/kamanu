# The x402 rail (card X2a)

The first of EXONUMIA's four measured rails: an x402 buyer client paying a seller this process runs
itself, through a facilitator, on Base Sepolia (`eip155:84532`) in testnet USDC. The other three
rails (X2b to X2d) follow this shape: an adapter module `exonumia.rails.<rail>`, one command, a row,
a raw log, and an offline gate with its own simulator.

```
python -m exonumia.rails hunt x402 --scope docs/rails/x402-scope.json --row rails/rows/x402-base-sepolia.json --cap 5000
```

That runs `kamanu.hunt.row.hunt_row` on the adapter's engine object with race_rate 0.03 and miss 0.05,
so every parallel test holds `trials_for(0.03, 0.05)` = 99 trials. It then adds two more sessions
behind every `fails` cell, so each finding has three, and runs the rail's four tests, 99 valid trials
each. It writes

* `rails/rows/x402-base-sepolia.json`: the row (H4's row plus `rail`, `network`, `chain_id`,
  `evidence`, `client`, `facilitator`, `third_party: true`, `notified`, `limits`, `rail_tests`,
  `confirmations`). Rule E5: it is someone else's product. This card does not add it to `site/` or
  to the registry.
* `evidence/rails/x402/<UTC date>/run.json`: every request and response body verbatim, every
  transaction hash kept, every address and key redacted (`exonumia.rails.x402.redact`). The payment
  headers (`PAYMENT-SIGNATURE`, `PAYMENT-REQUIRED`, `X-PAYMENT`) are base64 of JSON on the wire. The
  log keeps them as decoded JSON text so that redaction reaches the addresses inside them.
* `run.journal.jsonl` and `segments.json` beside `run.json`: the run's journal of finished pieces, and how
  the run was cut and resumed (`--resume`; [resume.md](resume.md), card X9).

Exit codes: 0 written; 2 usage; 3 refused (rule E4); 4 the live rail is not ready.

## What the owner provides

* `X402_TEST_KEY`: a Base Sepolia private key holding testnet USDC (https://faucet.circle.com). The
  buyer needs no ETH: x402's exact scheme has the facilitator submit the EIP-3009 transfer and pay
  the gas. The key is read from the environment only and is never written to a row, a log or an
  error.
* The x402 Python client with its EVM and httpx extras:
  `pip install "x402[evm,clients]==2.29.0"`. Use a virtual environment made with
  `--system-site-packages` so that kamanu's own dependencies stay visible.
* Optional: `X402_RPC_URL`, a Base Sepolia JSON-RPC endpoint (default `https://sepolia.base.org`).

The seller's `payTo` is an address derived from the buyer's key, so the money that moves stays with
the owner. Preflight refuses to start unless the wallet holds `600 × cap` minor units and the
scope's `max_amount` and `ceilings.money` admit the whole run (see the scope file's note). At
`--cap 5000` that means 3 USDC. Measured on the gate's simulator at cap 10000, a run moved
0.35 USDC in 226 transfers with the documented client. A sequential live run takes hours: about
99 validity trials of some 35 seconds each, plus the hunt's waits.

## The limits, as read on 2026-11-23

| kind | exists | from | tests it is put to |
|---|---|---|---|
| payment-ceiling | yes | x402 Python 2.29.0 `client_base.py`: `SpendControls`, `allowed_assets[].max_amount_per_payment` | over-ask |
| budget | **no** | the same: the spend controls cap one payment and the assets allowed. Nothing sums payments: no cumulative budget, no per-period total, no count | none |
| balance | yes | x402 spec `scheme_exact_evm.md`: "**Verify** the `client` has sufficient balance of the `asset`." | over-ask |
| validity | yes | EIP-3009 `validBefore`; the client sets it from the seller's `maxTimeoutSeconds` | freeze |
| nonce | yes | EIP-3009: `"EIP3009: authorization is used"` | parallel, ambiguous |

A client limit that exists is put to every test it can be. A backstop is put to the tests where it
is the last thing standing. A test no limit is put to is reported `not exercised` with its reason
(rule L4). With this library every test is exercised: over-ask on the ceiling and the balance,
freeze on validity, parallel and ambiguous on the nonce.

## The tests

Each trial is one session with a fresh client.

* **over-ask**: one payment above the client's ceiling (it fails if the client signs), or above the
  wallet's balance as read just before (it fails if money moves).
* **freeze / validity**: a payment is signed and held by the seller, which sends it to `/settle`
  5 s or more after its `validBefore`. It fails if money moves.
* **parallel / nonce**: one signed payment whose payload the seller sends to `/settle` twice at
  once. It fails if money moves twice.
* **ambiguous / nonce**: a payment whose `/settle` moves money, after which the seller answers 5xx
  (`fail-after`) or holds its answer past the client's timeout (`timeout-after`). The seller then
  sends the payload to `/settle` again. It fails if money moves twice.

### Waits, and trials redone (card X8, kit x8-live)

On 2026-11-24 the public facilitator's `/verify` took 8 to 50 s in bursts (about 1 s otherwise), and 24 of
140 ambiguous trials were not the ones planned: the client's 20 s wait ran out before the seller sent
`/settle` or answered. The live port now bounds the facilitator itself and waits past that bound:

* each facilitator POST has its own HTTP limits: connect 5 s, write 5 s, read 20 s for `/verify` and
  60 s for `/settle`; `/verify` is asked at most 3 times, 1 s and 2 s apart. The slowest `/verify` the
  port allows is therefore 93 s, the slowest `/settle` 70 s;
* the client waits 98 s (that `/verify` plus 5 s) in a `timeout-after` trial, where only `/settle`
  has to be sent before it gives up, and 168 s in every other mode, whose answer follows `/verify`
  and `/settle`;
* a `timeout-after` seller holds its answer until 3 s after the client's own wait ran out;
* the port returns a payment only once the seller has finished it, so the late `/settle` is in its log.
* a hunt session's hold cannot be redone, so it is a long one (`hold_long`): its authorization is valid
  600 s, and `/verify` is asked up to 8 times, min(2^i, 30) s apart (at most 331 s). The client waits
  336 s for it. On 2026-11-25 at 05:58 UTC the facilitator was unreachable (connect timeouts) for about
  4 minutes. Three tries inside a 30 s authorization left 8 signed hunt holds unverified, and the seller
  answered 402. That run was stopped and is kept as a replaced journal.

A trial whose bodies still do not show its planned shape (for example a `/settle` sent after the client
gave up) is redone whole in a fresh session before it is journaled. The missed attempt is kept
verbatim, redacted, in `evidence/rails/x402/<date>/discarded.jsonl` and named, with its reason, in
`segments.json` (`discarded`). What it asked still counts against `ceilings.money`. When more than a
tenth of one test's trials would be redone, the run stops and says so. X2a's reading of `run.json`
is unchanged.

Every outcome is read from the bodies: the seller's 402, the paid request, the facilitator's answers
and the chain's receipt (status 1 and exactly one Transfer of the token for the amount). It is never
read from what the client library returned. That value is kept in each payment's `client` field for
comparison.

## Trials run side by side (card X10)

With `"concurrency": {"trials": K}` in the scope ([concurrency.md](concurrency.md)), the trials of each
pair declared independent run K at once. `exonumia.rails.x402.CONCURRENT` declares every pair the
adapter runs:

| pair | side by side | why |
|---|---|---|
| `over-ask/payment-ceiling` | yes | each trial has a fresh client whose own spend control refuses to sign. Nothing it reads is shared with another trial |
| `over-ask/balance` | **no** | it asks for the buyer wallet's balance + 1 to 7, read just before. Every other trial's transfer moves that balance |
| `freeze/validity` | yes | one EIP-3009 authorization with a random nonce and its own `validBefore`. Waiting it out reads only its own clock |
| `parallel/nonce` | yes | one authorization, presented twice at once. Its nonce is random, so no other trial's authorization can use it |
| `ambiguous/nonce` | yes | one authorization, presented again after an ambiguous answer. Same reason as `parallel/nonce` |
| `over-ask/budget`, `freeze/budget`, `parallel/budget`, `ambiguous/budget` | yes | each trial's budget belongs to its own fresh client. The x402 Python client has no budget, so these pairs never run (see *The limits*) |

The facilitator, not the buyer, submits each transfer and pays its gas, so the buyer's account nonce
is not involved. The facilitator's own account is involved, though, and it is shared by every trial:
each `/settle` is a transaction from that account. The live port therefore sends one trial's `/settle`
at a time (`Seller.settling`, a lock). A trial's own settles still go together: `parallel` presents one
payload twice at once, under one hold of the lock. With one trial at a time the lock is never waited
for, so a K = 1 run is unchanged.

The lock was added on 2026-11-25. That day's first X10 attempt ran 8 trials at once without it, and
settles of different trials raced at the facilitator:

* in 49 of 99 `parallel/nonce` trials both settles failed (`invalid_exact_evm_transaction_failed`),
  so nothing moved. X8's run 3, one trial at a time, had 3 of 99 such trials;
* 79 of the first 117 `ambiguous/nonce` sessions were not valid trials: the first `/settle` failed, so money never moved before the ambiguous answer.

That attempt was stopped and is kept (see *The X10 run* below). Hunt sessions never run side by side. The freeze trial waits `maxTimeoutSeconds + 6`
seconds from the hold's answer. That is past `validBefore` (the payment was signed before that answer)
and the same wait in every run, whatever the clock read.

## Rule E4, by construction

`exonumia.rails.x402.engine()` refuses (`Refused`, reason `network`) a port whose CAIP-2 network and
chain id are not a test network the adapter knows and agree with each other. It also refuses when the
scope names a network that is not such a test network, or when the port's network is not one the
scope lists. It refuses (reason `facilitator`) a facilitator URL the scope does not list. All of this
happens before it calls the port at all. Each session's client is registered for the scope's
networks only, and a seller asking to be paid on any other network is refused. A payment above
`x402.max_amount`, or one that would take the run's asked total past `ceilings.money`, is refused
(reason `ceiling`) before its request is sent. Refusal texts hold no private value.

The live port was exercised on 2026-11-23 against the real library and `https://x402.org/facilitator`
with an unfunded wallet. The client signed, the facilitator's `/verify` answered
`invalid_exact_evm_insufficient_balance`, nothing moved, and the buyer and seller addresses came out
redacted.
